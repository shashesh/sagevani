# SageVani website — design spec

- Date: 2026-10-05
- Status: Approved by the owner on 2026-10-05
- Implementation plans: [stage 1 — foundation](../plans/2026-10-05-stage-1-foundation.md)
- Decision record: [D-004](../../../docs/governance/decisions.md)
- Scope: the public blog website and its admin, from first build to launch

## 1. Summary

SageVani is a database-backed blog. A single Next.js application, with Payload CMS installed inside it, serves both the public site and an admin area at `/admin`. Supabase stores all data: Postgres for every table and Storage for images. Netlify hosts the application. This GitHub repository holds the website code (in `website/`) and the foundation documents, but no article content.

The site follows the Foundation Handbook. The four doors become topics, the four shapes become article types, and the four layers become editor blocks. The reader promise, the corrections policy and the difficulty guidance all become features.

## 3. Scope

### At launch

- Every public page in section 6 and every admin capability in section 8.
- At least six published pieces, following the handbook's Phase 3 opening collection. The site must show what SageVani is with only those six.

### Later, only when earned (handbook Phases 4–5)

Tags, series pages, a public glossary, audio, reading paths, reader accounts, and any public view counts. None of these is built at launch. The data model leaves room for them.

### Not in scope

Paid subscriptions, advertising, social login, multi-author publishing, and translations. Regional languages remain possibilities, not commitments.

## 4. Architecture

```text
Readers ─┐                         ┌─ Resend (email sending)
         ├─► Netlify: Next.js app ─┼─ Cloudflare Turnstile (spam checks)
Owner ───┘   ├ public site         └─ Google Analytics (after consent)
             ├ /admin (Payload)
             ├ reader endpoints
             └ cover / link-preview images
                    │
                    ▼
             Supabase: Postgres (all tables) + Storage (images)
```

- **One application.** Payload installs inside Next.js. The public site, the admin and the APIs deploy together.
- **Rendering.**
  - Public pages are rendered on the server, cached, and refreshed when content changes: on publish, on edit, and when a comment is approved.
  - Pages load data through Payload's local API, which runs inside the app rather than over HTTP.
  - Only likes, the comment form, subscribe, the theme toggle and the cookie banner run in the browser.
- **Database connection.** Netlify runs the app as serverless functions, which open many short-lived connections. Payload therefore connects through Supabase's connection pooler (transaction mode).
- **Database schema.** Payload's tables live in a dedicated schema called `payload`, not in Supabase's default `public` schema. Supabase automatically publishes a web API for the `public` schema, and Payload's tables, which include emails, must not be reachable through it. Row-level security is also switched on for these tables as a second lock.
  - Payload marks its `schemaName` option as experimental.
  - Its generated migration does not create the schema, so the first migration must begin with `CREATE SCHEMA IF NOT EXISTS "payload"`. This was found and fixed during stage 1 planning.
  - Tests check that every table lands in `payload` and none in `public`.
- **Images.** Images are stored in Supabase Storage through Payload's S3-compatible storage adapter, and served resized and optimized.
- **Email.** Resend sends confirmation emails, new-article emails and comment notifications to the owner. Bulk sends run as a background job, not inside the publish request.
- **Repository layout.**

  ```text
  website/
    docs/specs/                 design documents
    src/app/(frontend)/         public pages
    src/app/(payload)/          Payload admin and API
    src/collections/            collection definitions
    src/blocks/                 editor blocks (Verse, Tradition, Practice)
    src/components/             site components
    src/lib/                    utilities (slug, reading time, search text, rate limits)
    tests/                      unit, integration, e2e
  ```

  Netlify's base directory is `website/`.

## 5. Data model

All collections use Payload access control. "Owner" means the owner role; "assistant" means the drafting-only role (see section 8).

### 5.1 Content

**articles** — drafts and versions on, autosave on

| Field | Notes |
| --- | --- |
| title | Required |
| slug | Unique, plain ASCII. Generated from the title with diacritics removed (`māyā` → `maya`); editable |
| summary | One-sentence summary shown under the title and in lists |
| shape | Required: Vani Note, Inquiry Essay, Text / Story Study, Practice Journal |
| topics | Relationship to topics, zero or more (a piece may pass through several doors) |
| difficulty | Required. Options are configurable; ships with the proposed Beginner / Intermediate / Advanced until Q-01 is decided |
| background | "Helpful background" text for the Before-you-read box |
| readFirst | Array of suggested prior readings: an internal article or an external item (title, author, URL), plus why it helps |
| body | Lexical rich text with the Verse, Tradition and Practice blocks and image blocks |
| sources | Array: type (primary text, commentary, academic, living tradition, general), work, author or commentator, edition or translator, exact location, URL, access date, claim supported |
| coverTerm | Short term or phrase drawn on the generated cover; falls back to the title |
| coverImage | Optional upload; replaces the generated cover |
| corrections | Array: date, what changed, whether to show a public note |
| editorialChecklist | Admin-only checkboxes mirroring `templates/editorial-review.md`; never public and never blocks publishing |
| sendEmail | Whether to email subscribers on first publish (default on) |
| publishedAt | Set automatically on first publish |
| readingTime | Minutes, computed on save |
| searchText | Plain text extracted from the title, summary and body on save; used for search |
| approval | Read-only: the approved version id, the approval time and the approver, set on publish |
| emailSentAt, emailRecipients | Read-only: send record |
| seo | Optional title and description overrides |

**Publish validation** (runs only when the status becomes published):

- `difficulty` is set.
- Advanced articles have at least one `readFirst` item.
- Text / Story Studies have at least one source.
- Every image in the body has alt text.

#### Editor blocks

- **Verse:** Devanagari (optional), transliteration, translation, text name, location, translator or edition.
- **Tradition:** school or teacher (required), interpretation text.
- **Practice:** invitation text.
- Reflection is ordinary body text and needs no block.

**topics** — the four doors: name, slug, question, intro, display order, cover tint.

**pages** — title, slug, Lexical body. Covers About, How SageVani writes, Start here (an introduction; the reading list itself is in site settings) and Privacy.

**media** — upload with required fields for alt text, creator, source, and license or permission, plus notes. This matches the provenance rule in `assets/README.md`.

### 5.2 Reader-created

**commenters** — email (unique, owner-only), display name, a trusted flag, and a hashed commenter token.

- When someone first comments, their browser receives a random token in a first-party cookie, and the database stores its hash.
- Approving that first comment marks the commenter trusted.
- Later comments skip moderation only when both the email and the browser token match. A trusted email used from another browser goes to pending, so knowing someone's email isn't enough to post unmoderated as them.

**comments** — article, commenter, display name, body (plain text, maximum 3,000 characters), status (pending, approved, spam, deleted), parent (one level of replies), isAuthorReply.

- The public can read approved comments only, and never the email field.

**likes** — article, visitorId (random id stored in a first-party cookie), createdAt.

- A unique index on (article, visitorId) enforces one like per browser per article.

**articleStats** — article, day, views, fullReads.

- A unique index on (article, day) keeps one row per article per day, and requests add to it.
- No IP addresses or personal data are stored.

**subscribers** — email (unique), status (pending, confirmed, unsubscribed), confirmToken, unsubscribeToken, confirmedAt.

- Sign-up requires email confirmation.

**rateLimits** — key (action plus a hashed IP plus a time window), count, expiresAt.

- Used by the reader endpoints. Hashed IPs are kept only until the window expires.

### 5.3 Site

**siteSettings** (global) — the featured article, up to three featured picks, the Start-here reading list (ordered articles), navigation, the footer motto, and the tagline ("Where silence learns to speak.").

**users** — email, name, role (owner or assistant). Login is locked after repeated failures. Only assistant accounts can hold an API key; the owner signs in with a password only.

### 6.1 Pages and routes

| Route | Content |
| --- | --- |
| `/` | Landing page: navigation; featured article (large cover, summary, byline, date, reading time, difficulty); Featured (three cards); Latest articles (list with thumbnails) and a sidebar (About box, Start here, topics with counts); the four-questions band; subscribe; footer |
| `/articles` | All published articles, newest first; filter by topic, shape and difficulty; paginated |

### 6.2 Article page

From top to bottom:

1. Site header, with a thin reading-progress line under it.
2. Topic and shape label, title, and summary. Then the byline (`Sagevani`), date, reading time and difficulty.
3. Cover (generated or photo).
4. **Before you read** box: background, then the suggested prior readings. Required for Advanced articles.
5. Body in a 680px centered column, including the Verse, Tradition and Practice blocks.
6. A like button with its count, and share options: copy link, WhatsApp, email, X.
7. Sources, in a collapsible list.
8. A correction note, shown only when one exists.
9. Comments: approved comments, with owner replies labelled "Author". Then the form: name, email (never shown), comment. A note says first comments are read before they appear.
10. Three more articles from the same topic.

### 6.3 Reader interactions

- **Likes**
  - Clicking updates the count immediately, then saves.
  - On failure the count reverts quietly.
  - The count is fetched in the browser, so cached pages never show a stale number.
- **Comments**
  - Turnstile and rate limits check each comment on the server.
  - A new commenter's comment is held as pending, and the reader sees "Thanks — your comment will appear once it has been read."
  - Trusted commenters' comments are approved immediately when posted from the same browser (section 5.2).
  - Approving a comment refreshes the article page.
  - On failure, the typed text is kept and a message is shown.
- **Views and full reads**
  - A view is recorded when an article opens, at most once per browser session per article.
  - A full read is recorded when the reader reaches the end of the body.
  - Requests from known bot user agents are ignored.
- **Subscribe**
  - The form is checked by Turnstile and rate limits.
  - The reader gets a confirmation email, and every email carries an unsubscribe link and a `List-Unsubscribe` header.
- **Theme**
  - The site follows the device setting, and the toggle overrides it.
  - The choice is stored in the browser and applied before the page first renders, so there's no flash of the wrong theme.

### 6.4 Search

- Postgres full-text search over `searchText`, using the `unaccent` extension, so "maya" matches "māyā" and "shankara" queries can be tuned to match "Śaṅkara".
- Partial-word matching is a fallback for short queries.
- The implementation must test that every IAST character in section 7.2 folds as expected. If the default `unaccent` rules miss any, add custom rules.

### 6.5 Generated covers

- On the site, covers are drawn in HTML and CSS: topic tint, cover term in large italic Literata, title, and a small SageVani mark. They stay sharp at any size and cost no image requests.
- For link previews, `/og/[slug]` renders the same design as a 1200×630 image with Next.js `ImageResponse`, embedding the Literata font files.
- When an article has a cover photo, the photo replaces the generated cover in both places.

### 7.2 Typography

- **Literata**, served from the site's own domain through `next/font`, with the `latin` and `latin-ext` subsets.
  - A check of the font file confirmed it contains every IAST character: ā ī ū ṛ ṝ ḷ ḹ ṃ ḥ ṅ ñ ṭ ḍ ṇ ś ṣ, and their capitals.
  - Article body: 19px with 1.7 line height. Interface text: 14–17px.
  - Headings: weight 500. The wordmark is italic.
  - Labels: 11px spaced capitals in the accent color.
- **Tiro Devanagari Sanskrit**, loaded only when a page contains a Devanagari verse.
- **Fonts checked and ruled out** for missing IAST characters:
  - Lora, Newsreader and IBM Plex Sans are missing ṛ ṃ ḥ ṣ ṭ ḍ ṇ.
  - Fraunces is missing ṅ.
- **URLs** stay plain ASCII. Displayed titles keep their diacritics.

### 7.3 Layout

- The reading column is 680px wide; the page container is 1120px.
- The layout is designed for phones first:
  - Under 860px, navigation collapses into a menu and grids drop to one or two columns.
  - Test widths: 320, 375, 768, 1024, 1440 and 1920 pixels.
- Motion is limited to the progress line and hover states, and respects reduced-motion settings.
- The design avoids decorative religious clip art, sunset gradients and stock meditation imagery.

## 8. Admin and publishing workflow

### 8.1 Roles

| Role | Can | Cannot |
| --- | --- | --- |
| Owner | Everything: write, publish, unpublish, moderate, see statistics, manage settings and users | — |
| Assistant | Through its API key: create and edit article drafts, upload media, read published content | Use the admin panel, publish or unpublish, delete, read commenter or subscriber emails, read statistics, change settings, edit any account (including its own password and API key), unlock accounts |

The assistant role enforces decision D-003: the assistant may draft without asking, and publication requires owner approval. AI drafting uses an assistant API key. SageVani is a solo project, so only the owner uses the admin panel (D-005). The rule that the assistant must not invent personal experiences or verification still applies to drafted content.

### 8.2 Writing

- The editor sits in the centre and the article fields in a side panel.
- The block menu inserts Verse, Tradition, Practice and image blocks.
- Drafts save automatically. Version history lets you compare any two versions.
- Preview shows the draft in the site's design before publishing.

### 8.3 Publishing and approval

- **Publishing is the owner's approval.** On publish, a hook records the approved version id, the time and the approver in `approval`, and sets `publishedAt` the first time.
- **Publish validation** (section 5.1) must pass.
- **The editorial checklist** is shown as a reminder and is never treated as approval.
- **After publish:**
  - The article, home page, its topic pages, `/articles`, the RSS feed and the sitemap refresh.
  - If `sendEmail` is on and no email has been sent yet, a background job emails confirmed subscribers (title, summary, cover, link, unsubscribe link) and records `emailSentAt` and the recipient count.
  - Edits never re-send the email.
- **Editing a published article** creates a new version. Publishing that version records a new approval.
- **Corrections:** add an entry with a date and a description of what changed. Public notes appear on the article and on `/corrections`.
- **Unpublishing** removes the page from the site and keeps the record and its history.

### 8.4 Moderation

- **Queue:** comments are listed by status, with pending ones first.
- **Actions:** approve, mark as spam, delete, or reply as Sagevani (the reply is approved automatically and labelled "Author").
- **Notifications:** the owner gets an email when a comment is pending.

### 8.5 Statistics

An owner-only admin dashboard shows:

- views, full reads, likes and comments per article, for the last 30 days and all time
- a most-read list
- subscriber counts

Google Analytics separately reports traffic sources and audience.

### 8.6 Curation

Site settings holds the featured article, the three featured picks and the Start-here list.

## 9. Security

This section describes the finished site. Stage 1 delivers the admin login, database and secrets items. Reader endpoints arrive in stage 4, and rate limits and security headers in stage 6.

- **Admin login**
  - HTTPS only, with secure cookies.
  - Login is locked after repeated failures.
  - Login attempts are rate-limited, so nobody can keep the owner locked out by guessing (stage 6).
  - There is one owner account, and only the owner can use the admin panel.
  - On a new staging or production database, the owner account is created from the owner's machine (`owner:create`) before the site is first deployed.
  - If the owner password is lost or exposed, `owner:reset-password` sets a new one from the owner's machine. It also signs out every session, removes any API key and clears a login lock.
  - First-account sign-up is refused everywhere except local development and tests. That includes Payload's built-in `first-register` endpoint, which bypasses access rules, so nobody else can claim the owner account.
  - A partial unique index means the database can never hold two owners, even under concurrent sign-ups.
  - Only assistant accounts can hold an API key. The owner account cannot have one, so a leaked key can never act as the owner.
  - Payload's GraphQL API is turned off. The site uses only the REST and local APIs.
- **Access control** on every collection and on sensitive fields:
  - Emails are owner-only.
  - The public sees only published articles and approved comments.
- **Database**
  - Payload's tables live in the dedicated `payload` schema, which Supabase's web API does not publish.
  - Row-level security is enabled on those tables.
  - Connections use TLS, verified against Supabase's certificate authority (`DATABASE_CA_CERT`).
  - The service and database credentials stay on the server.
- **Reader endpoints**
  - Comment and subscribe requests are verified by Turnstile on the server.
  - Every reader endpoint is rate-limited.
  - Input is validated for length and type. Comments are stored and shown as plain text, with output escaped.
  - Likes are protected by the per-browser uniqueness rule and rate limits, not by Turnstile. Running Turnstile on every like click would slow the button down.
- **Secrets** live only in Netlify environment variables, never in the repository. The app checks at startup that every required variable is present.
- **Headers:** a Content Security Policy that allows only the site itself, Turnstile, Google Analytics and the Supabase Storage domain, plus HSTS, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy`.
- **Dependencies:** automated update pull requests. Payload ships security fixes often.

## 10. Privacy

- **Cookie banner:** Google Analytics loads only after consent, using Google Consent Mode with consent denied by default. Declining is as easy as accepting.
- **Data stored**
  - commenter and subscriber emails, never displayed
  - comment text
  - an anonymous like id in a first-party cookie
  - daily article statistics without IP addresses
  - hashed IPs only inside short rate-limit windows
- **Privacy page:** it explains all of the above, the services used (Supabase, Netlify, Resend, Cloudflare Turnstile, Google Analytics) and how to ask for deletion. The owner can delete a commenter's or subscriber's data from the admin.
- **Region:** readers are worldwide. The Supabase database is in East US (Ohio), next to Netlify's default region for the site's server code (D-005).

## 11. Error handling

- **Database unreachable:** cached pages keep serving. Reader actions show a short, polite message, and nothing the reader typed is lost.
- **Email:** sends are retried with backoff, and failures appear in the admin.
- **Server errors** are logged with context. Readers never see stack traces.
- **Error tracking:** Sentry's free plan reports both server and browser errors.
- **Missing pages:** an unknown slug returns 404, and an unpublished article returns 404.

## 12. Performance, SEO and accessibility

- **Targets:** LCP under 2.5 s, CLS under 0.1, INP under 200 ms on a mid-range phone.
- **How the targets are met:**
  - cached server rendering
  - fonts served from the site's own domain, with only the needed subsets
  - the Devanagari font loaded only where it's used
  - optimized and lazy-loaded images
  - minimal browser JavaScript, with comments loaded as the reader scrolls near them
- **SEO:**
  - per-page title and description
  - Article structured data (JSON-LD)
  - canonical URLs
  - sitemap, RSS, and link-preview images
- **Accessibility:**
  - WCAG AA contrast in both themes (section 7.1)
  - full keyboard use with visible focus states
  - alt text required on every image
  - semantic HTML and landmarks
  - reduced motion respected
  - `lang` attributes on Sanskrit and Devanagari spans

## 13. Testing

- **Unit tests (Vitest):**
  - slug generation and diacritic folding
  - reading time and search-text extraction
  - publish validation rules and rate-limit logic
- **Integration tests** against a test Postgres:
  - access control: the public can't read emails; the assistant can't publish, delete or read statistics
  - the approval record on publish
  - send-once email logic
  - comment trust flow, like uniqueness and stats upserts
- **End-to-end tests (Playwright):**
  - reading an article
  - liking, and like persistence
  - a comment going to pending, then approval making it appear
  - subscribe, confirm and unsubscribe
  - publishing from the admin
  - searching "maya" to find "māyā"
  - the theme toggle and the cookie banner
- **Visual and accessibility checks:** screenshots at the section 7.3 widths in both themes, plus axe checks.
- **Continuous integration:** on pull requests and pushes to `main`, GitHub Actions runs lint, formatting and type checks, unit and integration tests with coverage, and a migrate-and-build on a fresh database. End-to-end tests run on pull requests. Netlify builds a deploy preview for each pull request.
- **Coverage:** at least 80%.

## 14. Environments and deployment

| Environment | App | Database |
| --- | --- | --- |
| Local | `next dev` | Postgres 17 in Docker (`docker compose`), with a separate test database |
| Preview | Netlify deploy previews (one per pull request) and branch deploys | A separate staging Supabase project (free plan); never production data |
| Production | Netlify production | Production Supabase project, in its own Supabase organization: free plan until the site is launch-ready, then Pro for backups and no pausing (D-005) |

- **Database changes** are Payload migrations, committed to the repository and followed by the schema hardening step.
  - Production deploys apply them automatically. Previews only build, so unreviewed branch code never runs migrations with database-owner credentials. The owner applies them to staging from their own machine.
  - Migrations connect through Supabase's session pooler (`DATABASE_MIGRATION_URL`). The running app uses the transaction pooler (`DATABASE_URL`).
  - Scripts that load Payload against a real database run with `NODE_ENV=production`, so that development-mode schema push is off.
- **Domain:** buy it before launch and point it at Netlify, which issues HTTPS automatically.
- **Email:** verify the sending domain with Resend (SPF and DKIM) once the domain exists.

## 16. Build order

Each stage ends in something that can be reviewed. Implementation plans may be written one stage at a time.

1. **Foundation**
   - Next.js and Payload scaffold in `website/`.
   - Supabase connection through the `payload` schema.
   - Users and roles.
   - CI, environments, and checks for required environment variables.
2. **Content model and admin**
   - All collections and the editor blocks.
   - Publish validation and the approval record.
   - Media storage.
3. **Public site**
   - Design tokens and the Literata and Tiro fonts.
   - Layout, header and footer, light and dark themes.
   - Landing, article, topic, archive and fixed pages.
   - Generated covers and link-preview images.
4. **Reader interactions**
   - Likes, comments and moderation.
   - Views and full reads, and the statistics dashboard.
   - Subscribe and the new-article email.
5. **Discovery and compliance:** search, RSS, sitemap, structured data, Google Analytics with the cookie banner, and the privacy page.
6. **Hardening and launch**
   - Security headers, and rate limits on admin login and reader endpoints.
   - Sentry.
   - Performance and accessibility passes, and the full end-to-end suite.
   - Domain, sender verification, the production database's move to Supabase Pro, and the six launch pieces.
